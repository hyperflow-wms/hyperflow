# HyperFlow: a scientific workflow management system


![HyperFLow](https://img.shields.io/docker/v/hyperflowwms/hyperflow)
## Description

HyperFlow is a Workflow Management System (WMS) dedicated for scientific workflows. 

Browse the [wiki pages](https://github.com/balis/hyperflow/wiki) to learn more about the HyperFlow workflow model. 

## Getting started

### Installation
* Install Node.js 18 or later (http://nodejs.org)
* Install Redis (http://redis.io) 
* Install HyperFlow: 
  * As the Docker image `hyperflowwms/hyperflow` from Docker Hub. Each release is pushed as `hyperflowwms/hyperflow:v<version>`, for example `hyperflowwms/hyperflow:v1.11.1`; see [Running locally using Docker images](#running-locally-using-docker-images).
  * From a git clone:
    ```
    git clone https://github.com/hyperflow-wms/hyperflow.git
    cd hyperflow
    npm install
    npm install -g .
    ```
    `npm install` installs the dependencies into the clone. `npm install -g .` then links the clone into npm's global packages and installs the `hflow` and `hflow-recovery-analysis` commands into npm's global bin directory, so the clone must stay where it is. `hflow --version` run from a clone prints `0.0.0-dev`, because the repository does not carry a release version; see [Releasing](#releasing) for how release versions are set.

### Running locally
* Start the redis server: `redis-server`
* Run example workflows using command `hflow run <wf_directory>`, for example:<br>```hflow run ./examples/Sqrsum```

### Running locally using Docker images
* Use the latest Docker image for the HyperFlow engine, published in Docker Hub as `hyperflowwms/hyperflow` 
* You can build the image yourself: `make container`
* Start redis container:<br> 
```docker run -d --name redis redis --bind 127.0.0.1```
* Run workflow via HyperFlow container, for example:
```
docker run -a stdout -a stderr --rm --network container:redis \
       -e HF_VAR_WORKER_CONTAINER="hyperflowwms/soykb-workflow-worker" \ 
       -e HF_VAR_WORK_DIR="$PWD/input" \ 
       -e HF_VAR_HFLOW_IN_CONTAINER="true" \
       -e HF_VAR_function="redisCommand" \
       -e REDIS_URL="redis://127.0.0.1:6379" \
       --name hyperflow \
       -v /var/run/docker.sock:/var/run/docker.sock \
       -v $PWD:/wfdir \
       --entrypoint "/bin/sh" hyperflowwms/hyperflow -c "apk add docker && hflow run /wfdir"
```
Where
* `hyperflowwms/soykb-worker` is the name of the workflow worker container ([Soykb](https://github.com/hyperflow-wms/soykb-workflow) in this case)
* current directory contains `workflow.json`
* subdirectory `inputs` contains workflow input data 

Outputs:
* Directory `inputs` will contain files generated by the workflow run
* Directory `inputs/logs-hf` will contain logs of all workflow jobs

### Running in a Kubernetes cluster
See [HyperFlow Kubernetes deployment](https://github.com/hyperflow-wms/hyperflow-k8s-deployment) project for more information. 

#### Job creation and failed tasks
With the `k8sCommand` function and `HF_VAR_ADMISSION_CONTROLLER` unset, the engine creates a Kubernetes Job for each task, or for each group of tasks, and sends the job messages to Redis while the Job is being created. When the Kubernetes API server answers the create request with a transient error, the engine retries it. Transient errors are HTTP 5xx, 429, 409 other than `AlreadyExists` (such as a conflicting update of the namespace's resource quota), and connection errors and timeouts. The delay before retry *n* is drawn at random between half and all of min(2<sup>n-1</sup> s, 30 s). If the response carries a `Retry-After` header, the delay is at least that long, but never more than 30 s. A 409 `AlreadyExists` for the Job's own name counts as success only if an earlier attempt of the same creation had an unclear result: no HTTP status (a connection error or timeout), or HTTP 500, 503 or 504. Such an attempt may have stored the Job without the engine learning so. On the first attempt, or when the earlier attempts got only 429, other 409 errors or 5xx codes other than 500, 503 and 504 (such as 502), `AlreadyExists` is taken to mean that something other than this creation made the Job, and the creation fails at once. `AlreadyExists` for another name and other client errors, such as 400, 403, 404 or 422, are not retried either.

`HF_VAR_JOB_CREATE_RETRIES` sets the number of retries after the first attempt; 0 disables retries. With the default of 10 retries, the engine waits 1.5 to 3 minutes in total between attempts, or up to 5 minutes when the API server sends long `Retry-After` delays.

If the Job cannot be created, because the error is not retried or the retries run out, each of its tasks fails with exit code 1, as if its job had exited with that code. The engine then handles the task like any failed job:

* with `HF_VAR_STOP_WORKFLOW_WHEN_JOB_FAILED=1`, the engine exits with status 1, which stops the workflow; this takes precedence over `HF_VAR_BACKOFF_LIMIT`;
* with `HF_VAR_BACKOFF_LIMIT=N` (N > 0), the engine submits the task again, with a new Job, up to N times;
* with neither, the task stays failed and never completes, so the workflow does not finish.

The engine receives the exit codes of jobs from Redis in a completion loop. If that loop stops on an unexpected error, the engine logs the error and exits with status 1, because the tasks waiting on that loop could never complete.

## Local configuration files
You can provide workflow configuration through local configuration files:
* `workflow.config.json` -- main configuration file 
* `workflow.config.{name}.json` -- any number of secondary configuration files

The content from all configuration files will be merged and passed to workflow functions via `context.appConfig`. For example for files:
```
workflow.config.json:
{
  "main": "mainValue"
}

workflow.config.foo.json:
{
   "secondary": "secondaryValue"
}
```
The following will be passed in `context.appConfig`:
```
{
  "main": "mainValue",
  "foo": {
     "secondary": "secondaryValue"
  }
}
```

## HyperFlow server
The HyperFlow engine can be started in a server mode using command: ```hflow start-server```

If succesfully started, the server prints its URL:
```
HyperFlow server started at http://localhost:38775
```

Workflows can be run through the HyperFlow server as follows:

```
hflow run --submit=<hyperflow_server_url> <workflow_dir>
```

Currently `<workflow_dir>` must be a local directory accessbile by the server. This allows running multiple workflows (concurrently) using the same instance of the HyperFlow engine.

## Releasing
A release is a GitHub release whose tag is `v` followed by the version, for example `v1.11.2`. The tag is the only place the version is set. The maintainer creates the release from `master`:

```
gh release create v<version> --target master --generate-notes
```

The CI workflow (`.github/workflows/main.yml`) runs `tests/connector.js`, `tests/k8sJobSubmit.js` and `tests/version.js` and builds the image with `make image` on every push to `master`, on pull requests into `master`, on pushes of `v*.*.*` tags and on manual runs. When a release is published, it also runs `make push RELEASE_TAG="$GITHUB_REF_NAME" PRERELEASE="$PRERELEASE"`, with `PRERELEASE` set from the release's pre-release flag to `true` or `false`. This covers a release created without being saved as a draft, as by `gh release create` above, and a draft release when the maintainer publishes it later. For a release that is not a pre-release, `make push` builds the image at the release tag and pushes it to Docker Hub as `hyperflowwms/hyperflow:latest` and `hyperflowwms/hyperflow:v<version>`. A pre-release pushes only its own tag, such as `hyperflowwms/hyperflow:v1.11.2-rc.1`, and does not move `hyperflowwms/hyperflow:latest`. Changing a pre-release into a release later does not publish it again, so no image is pushed then. Publishing a release that is not a pre-release again, after converting it back to a draft, runs the same steps and moves `:latest` back to that release, even when newer releases exist. The image is published only from CI; do not run `make push` locally.

The released image tag must stay exactly `hyperflowwms/hyperflow:v<major>.<minor>.<patch>`, for example `hyperflowwms/hyperflow:v1.11.2`. Renovate in the `hyperflow-k8s-deployment` and `1000genome-workflow` repositories finds new engine images on Docker Hub by the pattern `hyperflowwms/hyperflow:v\d+\.\d+\.\d+`, so an image released under a tag of another form is never picked up there. Read this section before changing the release workflow, the version scheme or the image tag.

Publishing a pre-release is the way to get a test image of `master` onto Docker Hub:

```
gh release create v1.11.2-rc.1 --target master --prerelease --generate-notes
```

This pushes `hyperflowwms/hyperflow:v1.11.2-rc.1` and leaves `:latest` where it is. Renovate ignores such a tag, because it is not of the form `v<major>.<minor>.<patch>`.

With `RELEASE_TAG` set, `make image` and `make push` take the image tag and the version from it, and do not run `git describe`: `RELEASE_TAG=v1.12.0` tags the image exactly `v1.12.0` and passes `1.12.0` as the version, also when another tag, such as an annotated `v1.12.0-rc1` that `git describe` would pick, is on the same commit, and also when tracked files have uncommitted changes. The Makefile refuses to run when `RELEASE_TAG` is not one of the tags on the checked-out commit, or does not start with `v`. `make push` also refuses to run when `RELEASE_TAG` has nothing after the `v`, and when a `VERSION` or `TAG` given on the command line differs from what `RELEASE_TAG` gives.

`PRERELEASE` decides whether `make push` pushes the image as `:latest`. With `PRERELEASE=true` it pushes only the version tag; with `PRERELEASE=false`, or without `PRERELEASE`, it pushes `:latest` too. `make push` refuses any other value, an empty one included, before anything is built, so a mistyped value does not push `:latest`. `make -n push` prints `Push latest: yes` or `Push latest: no (PRERELEASE=true)`. The decision does not depend on the version: a version such as `1.11.2-3-gabc1234`, which `git describe` gives between releases, is a semver pre-release too, and `make push` without `PRERELEASE` pushes `:latest` for it. `make image` pushes nothing and ignores `PRERELEASE`. Make also reads `PRERELEASE` from the environment, so a `PRERELEASE` exported in the shell affects a local `make push`.

Without `RELEASE_TAG`, `make image` runs `git describe --tags --dirty` restricted to version tags, the tags that match `v[0-9]*.[0-9]*.[0-9]*`, such as `v1.11.2`; tags of other names, such as `prePersistence`, `v1.11` or `1.7.1`, are skipped. The result is the nearest version tag, followed by `-<commits>-g<hash>` between releases, and by `-dirty` when a tracked file has uncommitted changes. `make image` tags the image with that result and passes it, without its leading `v`, to `docker build` as the `VERSION` build argument, and the Dockerfile writes it into the image's `package.json` with `npm version`. `hflow --version` in the image prints that version: `1.11.2` in the image built at the release tag, and a version such as `1.11.2-3-gabc1234` in an image built three commits later. When no version tag is reachable, for example in a clone made with `--no-tags`, `make image` passes no version, tags the image with the abbreviated commit hash (followed by `-dirty` in the same way), and the image reports `0.0.0-dev`. `make push` publishes only an image with a version: when no version tag is reachable and no `VERSION` is given, it refuses to run, before anything is built, and so do `make` and `make all`, which push. Outside a git checkout, as in a source archive, `git describe` finds no commit, and `make image` refuses to run unless the image tag is given as `make image TAG=<tag>`.

The version must be a strict semver 2.0.0 version without build metadata, such as `1.11.2`, `1.12.0-rc.1` or `1.11.2-3-gabc1234-dirty`. `scripts/check-version.sh` checks it in two places. `make image` runs it before any docker command, so a tag that does not give such a version, such as `v1.12.03` or `v1.11.2.1`, fails before anything is built, tagged or pushed. The Dockerfile runs it before `npm version`, so `docker build --build-arg VERSION=...` fails for a value such as `patch`, `--help`, `1.2.3+build` or `1.12`. The Makefile passes the version and the image tag to the docker commands through the environment, never as text in a command line, so a tag name with characters that a shell interprets is not run.

`package.json` in the repository holds `0.0.0-dev`, and no commit changes it, so `hflow --version` run from a checkout or a source archive prints `0.0.0-dev`. Run `node tests/version.js` to check the version handling in the `Makefile` and the `Dockerfile` without Docker.

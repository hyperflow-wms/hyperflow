# HyperFlow: a scientific workflow management system


![HyperFLow](https://img.shields.io/docker/v/hyperflowwms/hyperflow)
## Description

HyperFlow is a Workflow Management System (WMS) dedicated for scientific workflows. 

Browse the [wiki pages](https://github.com/balis/hyperflow/wiki) to learn more about the HyperFlow workflow model. 

## Getting started

### Installation
* Install Node.js 18 or later (http://nodejs.org)
* Install Redis (http://redis.io) 
* Install HyperFlow: 
  * As the Docker image `hyperflowwms/hyperflow` from Docker Hub. Each release is pushed as `hyperflowwms/hyperflow:v<version>`, for example `hyperflowwms/hyperflow:v1.11.1`; see [Running locally using Docker images](#running-locally-using-docker-images).
  * From a git clone:
    ```
    git clone https://github.com/hyperflow-wms/hyperflow.git
    cd hyperflow
    npm install
    npm install -g .
    ```
    `npm install` installs the dependencies into the clone. `npm install -g .` then links the clone into npm's global packages and installs the `hflow` and `hflow-recovery-analysis` commands into npm's global bin directory, so the clone must stay where it is. `hflow --version` run from a clone prints `0.0.0-dev`, because the repository does not carry a release version; see [Releasing](#releasing) for how release versions are set.

### Running locally
* Start the redis server: `redis-server`
* Run example workflows using command `hflow run <wf_directory>`, for example:<br>```hflow run ./examples/Sqrsum```

### Running locally using Docker images
* Use the latest Docker image for the HyperFlow engine, published in Docker Hub as `hyperflowwms/hyperflow` 
* You can build the image yourself: `make container`
* Start redis container:<br> 
```docker run -d --name redis redis --bind 127.0.0.1```
* Run workflow via HyperFlow container, for example:
```
docker run -a stdout -a stderr --rm --network container:redis \
       -e HF_VAR_WORKER_CONTAINER="hyperflowwms/soykb-workflow-worker" \ 
       -e HF_VAR_WORK_DIR="$PWD/input" \ 
       -e HF_VAR_HFLOW_IN_CONTAINER="true" \
       -e HF_VAR_function="redisCommand" \
       -e REDIS_URL="redis://127.0.0.1:6379" \
       --name hyperflow \
       -v /var/run/docker.sock:/var/run/docker.sock \
       -v $PWD:/wfdir \
       --entrypoint "/bin/sh" hyperflowwms/hyperflow -c "apk add docker && hflow run /wfdir"
```
Where
* `hyperflowwms/soykb-worker` is the name of the workflow worker container ([Soykb](https://github.com/hyperflow-wms/soykb-workflow) in this case)
* current directory contains `workflow.json`
* subdirectory `inputs` contains workflow input data 

Outputs:
* Directory `inputs` will contain files generated by the workflow run
* Directory `inputs/logs-hf` will contain logs of all workflow jobs

### Running in a Kubernetes cluster
See [HyperFlow Kubernetes deployment](https://github.com/hyperflow-wms/hyperflow-k8s-deployment) project for more information. 

#### Job creation and failed tasks
With the `k8sCommand` function, the engine creates a Kubernetes Job for each task, or for each group of tasks, and sends the job messages to Redis while the Job is being created. With `HF_VAR_ADMISSION_CONTROLLER=1`, the engine first waits for a permit from the [admission controller](functions/kubernetes/ADMISSION_CONTROLLER.md), which records each failed create request in its error rate. When the Kubernetes API server answers the create request with a transient error, the engine retries it. Transient errors are HTTP 5xx, 429, 409 other than `AlreadyExists` (such as a conflicting update of the namespace's resource quota), and connection errors and timeouts. The delay before retry *n* is drawn at random between half and all of min(2<sup>n-1</sup> s, 30 s). If the response carries a `Retry-After` header, the delay is at least that long, but never more than 30 s. A 409 `AlreadyExists` for the Job's own name counts as success only if an earlier attempt of the same creation had an unclear result: no HTTP status (a connection error or timeout), or HTTP 500, 503 or 504. Such an attempt may have stored the Job without the engine learning so. On the first attempt, or when the earlier attempts got only 429, other 409 errors or 5xx codes other than 500, 503 and 504 (such as 502), `AlreadyExists` is taken to mean that something other than this creation made the Job, and the creation fails at once. `AlreadyExists` for another name and other client errors, such as 400, 403, 404 or 422, are not retried either.

`HF_VAR_JOB_CREATE_RETRIES` sets the number of retries after the first attempt; 0 disables retries. With the default of 10 retries, the engine waits 1.5 to 3 minutes in total between attempts, or up to 5 minutes when the API server sends long `Retry-After` delays.

If the Job cannot be created, because the error is not retried or the retries run out, each of its tasks fails with exit code 1, as if its job had exited with that code. The engine then handles the task like any failed job:

* with `HF_VAR_STOP_WORKFLOW_WHEN_JOB_FAILED=1`, the engine exits with status 1, which stops the workflow; this takes precedence over `HF_VAR_BACKOFF_LIMIT`;
* with `HF_VAR_BACKOFF_LIMIT=N` (N > 0), the engine submits the task again, with a new Job, up to N times;
* with neither, the task stays failed and never completes, so the workflow does not finish.

The engine receives the exit codes of jobs from Redis in a completion loop. If that loop stops on an unexpected error, the engine logs the error and exits with status 1, because the tasks waiting on that loop could never complete.

## Local configuration files
You can provide workflow configuration through local configuration files:
* `workflow.config.json` -- main configuration file 
* `workflow.config.{name}.json` -- any number of secondary configuration files

The content from all configuration files will be merged and passed to workflow functions via `context.appConfig`. For example for files:
```
workflow.config.json:
{
  "main": "mainValue"
}

workflow.config.foo.json:
{
   "secondary": "secondaryValue"
}
```
The following will be passed in `context.appConfig`:
```
{
  "main": "mainValue",
  "foo": {
     "secondary": "secondaryValue"
  }
}
```

## HyperFlow server
The HyperFlow engine can be started in a server mode using command: ```hflow start-server```

If succesfully started, the server prints its URL:
```
HyperFlow server started at http://localhost:38775
```

Workflows can be run through the HyperFlow server as follows:

```
hflow run --submit=<hyperflow_server_url> <workflow_dir>
```

Currently `<workflow_dir>` must be a local directory accessbile by the server. This allows running multiple workflows (concurrently) using the same instance of the HyperFlow engine.

## Releasing
The maintainer releases from `master`:

```
gh release create v<version> --target master --generate-notes
```

When the release is published, CI (`.github/workflows/main.yml`) builds the image and pushes it to Docker Hub as `hyperflowwms/hyperflow:v<version>` and `hyperflowwms/hyperflow:latest`. The image is published only from CI, because a local `make push` tags the image from that machine's `git describe`.

A pre-release needs a `-suffix` in its tag, such as `v1.12.0-rc.1`:

```
gh release create v1.12.0-rc.1 --target master --prerelease --generate-notes
```

CI refuses to publish when the tag's form and the release's pre-release flag disagree: a tag with a `-suffix` must be published with `--prerelease`, and a plain `vX.Y.Z` without it. A tag that contains `-` is pushed under its own tag only and leaves `:latest` alone. This is the way to get a test image of `master`. Promoting a pre-release to a release later publishes nothing, because GitHub then sends a `released` event, not `published`; the stable version needs its own release.

The released image tag must stay exactly `hyperflowwms/hyperflow:vX.Y.Z`, for example `hyperflowwms/hyperflow:v1.11.2`. Renovate in `hyperflow-k8s-deployment` and `1000genome-workflow` finds new engine images by the pattern `hyperflowwms/hyperflow:v\d+\.\d+\.\d+`, so it never picks up a tag of another form.

`package.json` in the repository holds `0.0.0-dev`. The image build writes the tag's version into the image's `package.json`, so `hflow --version` in the image prints it. `node tests/makePush.js` checks which image tags `make push` pushes for a given tag.
